# ENCOR 350-401 – IP Multicast Routing Lab

## 1. Lab Overview

This lab demonstrates IP multicast routing using Cisco IOS XE routers in PNETLab.

The objective is to understand how multicast traffic is distributed from a source to multiple receivers using Protocol Independent Multicast Sparse Mode (PIM-SM).

### Technologies Covered

- IP Multicast
- PIM Sparse Mode (PIM-SM)
- Internet Group Management Protocol (IGMP)
- Rendezvous Point (RP)
- Reverse Path Forwarding (RPF)
- Shared Tree (`(*,G)`)
- Source-Specific Tree (`(S,G)`)
- PIM Register process
- Multicast Routing Table Verification

## 5. Multicast Configuration

### Enable multicast routing

Configured globally on all routers:

```cisco
ip multicast-routing
```

### Enable PIM Sparse Mode

PIM Sparse Mode was enabled on all participating routed interfaces:

```cisco
interface GigabitEthernet0/0
 ip pim sparse-mode
```

The equivalent configuration was applied to the other participating interfaces.

### Configure the Rendezvous Point

R2 Loopback0 was used as the RP:

```cisco
interface Loopback0
 ip address 2.2.2.2 255.255.255.255
 ip pim sparse-mode
```

Static RP configuration on all routers:

```cisco
ip pim rp-address 2.2.2.2
```

### Configure receiver membership

For the initial receiver test, router-based IGMP membership was configured:

On R3:

```cisco
interface GigabitEthernet0/1
 ip igmp join-group 239.1.1.1
```

On R4:

```cisco
interface GigabitEthernet0/1
 ip igmp join-group 239.1.1.1
```

Note: `ip igmp join-group` creates local membership on the router. This lab therefore demonstrates router-generated membership rather than actual IGMP reports generated by PC2 and PC3.

## 6. Verification

The following commands were used:

```cisco
show ip pim neighbor
show ip pim rp mapping
show ip igmp groups
show ip mroute
show ip mroute 239.1.1.1
show ip rpf 2.2.2.2
show ip route 2.2.2.2
```

### PIM Neighbour Verification

R1 successfully established a PIM adjacency with R2.

```text
Neighbor          Interface
10.0.12.2         GigabitEthernet0/0
```

### IGMP Membership Verification

R3 and R4 displayed membership for multicast group:

```text
239.1.1.1
```

### Shared Tree Verification

R3 displayed:

```text
(*, 239.1.1.1)
Incoming interface: GigabitEthernet0/0
RPF nbr: 10.0.23.1

Outgoing interface list:
GigabitEthernet0/1, Forward/Sparse
```

This confirmed that R3 had established shared-tree forwarding state towards its receiver LAN.

R2 displayed:

```text
(*, 239.1.1.1)
RP 2.2.2.2

Outgoing interface list:
GigabitEthernet0/2, Forward/Sparse
GigabitEthernet0/1, Forward/Sparse
```

This confirmed that the RP had both receiver branches in its outgoing interface list.

### RPF Verification

On R1:

```text
show ip rpf 2.2.2.2
```

The result confirmed:

```text
RPF interface: GigabitEthernet0/0
RPF neighbor: 10.0.12.2
RPF type: unicast (ospf 1)
```

This demonstrated that R1 used its unicast OSPF routing information to determine the correct upstream path towards the RP.

### Multicast Source Test

On R1:

```cisco
ping 239.1.1.1 source 192.168.10.1
```

Observed responses:

```text
Reply from 192.168.40.1
Reply from 192.168.30.1
```

Both receiver-side routers responded, demonstrating successful multicast delivery through the configured network.

### Source-Specific State

R1 displayed:

```text
(192.168.10.1, 239.1.1.1)
Incoming interface: GigabitEthernet0/1

Outgoing interface list:
GigabitEthernet0/0, Forward/Sparse
```

R2 also learned the source:

```text
(192.168.10.1, 239.1.1.1)
Incoming interface: GigabitEthernet0/0
RPF nbr: 10.0.12.1

Outgoing interface list:
GigabitEthernet0/1
GigabitEthernet0/2
```

R3 and R4 displayed both shared-tree and source-specific entries.

## 7. Key Learning Outcomes

1. PIM Sparse Mode uses a Rendezvous Point to establish shared multicast distribution.
2. IGMP allows receivers to express interest in multicast groups.
3. RPF checks use unicast routing information to validate the upstream path.
4. `(*,G)` represents shared-tree state.
5. `(S,G)` represents source-specific multicast state.
6. The RP maintains multicast forwarding state for active sources and receiver branches.
7. Shared-tree and source-specific entries can coexist.
8. The presence of an `(S,G)` entry alone does not prove that a downstream router has switched to a direct shortest-path tree.

## 8. Conclusion

The lab successfully demonstrated multicast routing using PIM Sparse Mode, static RP configuration, IGMP membership, RPF verification and multicast forwarding.

The practical exercise provided an opportunity to inspect multicast routing tables and understand how shared-tree and source-specific forwarding state are maintained.
